# FL-001: Typed JSON-RPC request-id isolation

## Hypothesis

JSON-RPC 2.0 ids are a String or a Number, so `7` and `"7"` are **different
ids**. MCP 2025-11-25 ("Requests MUST include a string or integer ID") adds
cancellation by id. An implementation that keys any per-request table by
`str(id)` or folds `"7"` to `7` merges two live requests. The merge shows up as
lost responses, misrouted responses, or a cancellation that hits the wrong
request.

## Design

* **Deterministic completion.** Each request calls `gate(tag)`, which blocks
  inside the server until the harness calls `release(tag)`. Out-of-order
  completion is part of the scenario, not a timing accident.
* **Raw wire client.** The harness writes raw JSON-RPC itself, so no SDK
  client "helps" with id handling.
* **Matched controls.** Each collision scenario is paired with controls that
  have the same shape but ids that cannot collide (`7`/`8`, `"a7"`/`"b7"`,
  `7`/`"x7"`).
* **Spec-based oracle.** Rules R1-R7 and WIRE in
  [`oracle.py`](../src/mcp_faultline/oracle.py), each tied to a JSON-RPC 2.0 or
  MCP 2025-11-25 clause. SHOULD-level cancellation behaviour is reported as an
  observation, never as a failure.
* **Negative controls.** Five planted mutants and five injected faults. The
  oracle must flag each one exactly on the scenarios where it can occur, and
  stay quiet on all others (`faultline controls`: 11/11 hold).

## Scenario matrix

8 id pairs × 3 shapes = 24 scenarios, plus seeded random scenarios.

| pair | kind | shapes |
|---|---|---|
| `7`/`"7"`, `"7"`/`7`, `0`/`"0"`, `-1`/`"-1"` | collision | out-of-order, cancel-first, cancel-second |
| `7`/`"07"` | non-canonical (python-sdk#3432) | same |
| `7`/`8`, `"a7"`/`"b7"`, `7`/`"x7"` | control | same |

### Finding A: python-sdk cross-cancellation on every transport (dispatcher layer)

`JSONRPCDispatcher` registers inbound requests as
`_in_flight[coerce_request_id(req.id)]`. While `7` and `"7"` are both in
flight, the second registration overwrites the first. A
`notifications/cancelled` for the **earlier** id then cancels the **later**
one, and the earlier one can no longer be cancelled at all.

Minimised automatically from a 16-step random scenario (seed 6) to 3 steps in
31 runs, then confirmed 3/3:

```
call   id="9007199254740991" gate(g0)
call   id=9007199254740991  gate(g3)
cancel id="9007199254740991"
-> 9007199254740991 never receives a response (R3, R6); the cancelled one completes
```

Stdlib-only reproduction:
[`evidence/fl001/minimized/repro_py_stdio_random_seed_6_min.py`](../evidence/fl001/minimized/repro_py_stdio_random_seed_6_min.py).

**Relation to known issues.** This is the canonical-id consequence of the same
deliberate coercion discussed in #3432, and it overlaps in symptoms with
#3786. It is **not** caused by the Streamable HTTP `str()` keys: it reproduces
on stdio. Fix experiments (patched copies of 2.3.0, never the pinned install):

| patch | stdio (24) | HTTP SSE (24) | HTTP JSON (24) |
|---|---|---|---|
| none (2.3.0) | 19 pass | 11 pass | 11 pass |
| HTTP stream keys only (the shape proposed in #3786) | 19 pass | 19 pass | not run |
| dispatcher only (exact-typed `_in_flight`, twin fallback on cancel lookup) | **24 pass** | 12 pass | 12 pass |
| both | **24 pass** | **24 pass** | **24 pass** |

So the fix proposed in #3786 is necessary but not sufficient: `cancel-first`
still fails on HTTP and on stdio until the dispatcher stops keying `_in_flight`
by the coerced id. Note also that the coercion's docstring claims TS parity,
but the TS **server** keys by typed id and passes every case. Parity holds
only for TS's client-side response correlation.

### Finding B: python-sdk Streamable HTTP routes by `str(id)`. Known: python-sdk#3786

Reproduced in both response modes. Over HTTP the cross-cancellation also
produces `{"id":"7","error":{"code":-32800}}` for a request that was never
cancelled (R4+R6). Over stdio the same collision drops the response silently.

### Finding C: TS v1 ignores cancellation of request id 0. Known: typescript-sdk#2283 / #3043

`if (!notification.params.requestId) return;` treats `0` as absent. Ignoring a
cancellation is SHOULD-level, so FL-001 reports it as an observation. TS v2
2.4.0 handles it correctly (differential test
`test_typescript_v2_honours_cancel_of_request_id_zero`).
